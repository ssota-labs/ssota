ADR-runtime-ontology-with-closed-edit-vocabulary

Runtime Ontology with a Closed Edit Vocabulary

stage
accepted
summary
타입과 선언적 액션은 런타임 데이터로 정의하고 로직은 생성된 코드로 sandbox에서 실행한다. 모든 편집은 닫힌 어휘를 거쳐 단일 커밋 경로로 모인다.
supersedes
ADR-relational-domain-cores-with-graph-projections

Context

SSOTA의 목표는 회사가 자기 업무 도메인(법무·회계 등)을 런타임에 정의해 에이전트와 함께 운영하는 환경이다. 이는 Palantir 온톨로지가 지향하는 바와 같으므로, 그쪽 구조를 조사해 채택 가능성을 판단했다.

조사 결과 Palantir은 타입과 선언적 액션만 런타임 저작한다. Ontology Manager(노코드 UI)에서 object type·link type·declarative action을 만들지만, Function은 Code Repository의 코드이며 git 브랜치·태그·릴리즈를 거쳐 배포되고 Ontology Manager에서 버전을 선택한다. 선언적 액션이 성립하는 이유는 표현력을 의도적으로 낮게(속성 설정·객체 생성·링크 생성·삭제) 유지하고 그 이상을 전부 코드로 넘기기 때문이다.

또한 Palantir이 “타입마다 스키마”를 마이그레이션 없이 얻는 것은 backing datasource가 객체 스토리지 위의 Parquet(schema-on-read)이고 별도 인덱싱 서비스가 서빙하기 때문이다. SSOTA는 Postgres/Supabase이므로 그 공짜 점심이 없다. RDBMS에서 런타임 사용자 정의 타입을 지원하는 선택지는 사실상 범용 테이블 + 메타데이터뿐이다 — Salesforce도 커스텀 오브젝트·필드에 물리 테이블이나 컬럼을 만들지 않고 메타 테이블 + 범용 컬럼으로 처리한다.

반면 SSOTA에는 Palantir에 없던 자산이 둘 있다. (1) 자연어 요청을 타입 있는 코드로 바꾸는 코딩 에이전트, (2) teamspace 단위 sandbox 인프라(SandboxHandle, sandbox_environments/sandbox_sources/sandbox_snapshots). 따라서 “로직도 프로젝트별로 동적”이라는 목표는 규칙 DSL 인터프리터가 아니라 생성된 코드의 sandbox 실행으로 달성할 수 있다.

선행 결정 ADR-relational-domain-cores-with-graph-projections는 도메인별 관계형 스키마를 정본으로 삼았다. DB 제약을 얻지만 타입 추가를 릴리즈에 묶어, 런타임 도메인 정의라는 제품 목표와 정면 충돌한다.

과거 generic runtime(executeAction + JSON rule 해석)은 저장소에서 제거되었다. 실패 원인은 “범용성” 자체가 아니라 액션의 행동을 데이터로 두고 런타임에 해석한 것이다. 이 결정은 그 실패를 반복하지 않도록 인터페이스는 데이터, 행동은 코드로 경계를 고정한다.

현행 구현 실측

이 결정은 그린필드가 아니다. 저장소를 감사한 결과 세 층이 고르게 비어 있는 것이 아니라 L3(함수)가 L2(액션)보다 훨씬 더 구현되어 있고, 가장 큰 실제 갭은 “동적 로직”이 아니라 검증 층이다.

  • L1 저장·저작 ✅ — node_catalog/edge_catalog에 property_schema·domain_catalog_ids·range_catalog_ids 컬럼이 있고, CatalogWritePort와 agent-runtime의 create_node_type/create_edge_type 도구로 이미 런타임 타입 저작이 가능하다.
  • L1 검증 ❌ (최우선 갭) — validateNodeProperties는 isKnownNodeType(catalogKey)일 때만 하드코딩된 contracts Zod로 파싱하고 런타임 정의 타입은 properties를 무검증 통과시킨다. validateEdgeProperties는 모든 타입에 대해 no-op이다. create-edge는 source/target 존재만 확인하고 domain_catalog_ids/range_catalog_ids를 읽지 않는다 — [GRAPH-05]의 edge domain/range 검증은 문서만 있고 미구현이다. 즉 카탈로그의 스키마 필드가 전부 불활성이다.
  • L2 criteria ✅ — Gate Policy 엔진이 이미 submission criteria에 해당한다. when(4 hooks) · match · require[](그래프 경로 표현식 + count{min,max} + ifMissing) · onFail(GATE_PENDING/GATE_REJECTED) · onPass.effects(닫힌 집합, 현재 spawn_task). 정책은 그래프 노드로 저장되어 런타임 로드된다. parseGatePath가 문법을 고정하므로 이미 닫힌 DSL이며, 애초 구상한 criteria kind 열거보다 표현력이 높다.
  • L2 쓰기 정의 ❌ — Gate는 “쓰기를 막는” 층이고 “쓰기를 정의하는” 층이 없다. 파라미터 스키마·편집 op 어휘·권한·감사 기록·단일 트랜잭션 커밋이 부재하다.
  • L3 ✅ (커밋 모델만 불일치) — workers 테이블이 함수 타입이다(input_schema·output_schema·script·runtime=vercel_sandbox·teamspace + optional account_id). executeWorker가 inputSchema 검증 · dryRun · permissions · 브로커된 SDK 브리지로 실행하며 sandbox 코드는 DB를 직접 만지지 않는다. 다만 SDK가 graph.createNode/updateNode/createEdge로 호출마다 커밋하므로 워커 1회 실행이 여러 독립 커밋이 되고 단일 트랜잭션·aggregate 락이 없다.
  • 에이전트 주변 ✅ — agent_definitions, schedules(cron + IANA tz), tasks, agent_runs/agent_run_messages, sandbox 4테이블 + SandboxHandle, skills(+GitHub discover·lock), Composio 및 Slack·Notion·GitHub·Linear·Discord 커넥터, chat.

따라서 이 결정은 새 층을 짓는 것이 아니라 (a) 비어 있는 검증 층을 채우고, (b) Gate 위에 쓰기 봉투를 얹고, (c) 워커 커밋 모델을 트랜잭션으로 모으는 것이다.

Decision

온톨로지를 세 층으로 나눈다. 인스턴스는 전부 nodes/edges에 저장하고 도메인 전용 테이블을 만들지 않는다.

  • L1 타입 — node_catalog/edge_catalog. 완전 동적(데이터). property_schema로 properties를 검증한다. DB 강제 불변식(invariants 컬럼)은 두지 않는다 — 아래 “불변식은 L3” 참조.
  • L2 선언적 액션 — 파라미터 스키마 + criteria + 편집 op. 완전 동적(데이터). 편집 op는 닫힌 집합이다. criteria는 새 어휘를 만들지 않고 기존 Gate Policy 엔진을 재사용한다 — parseGatePath가 문법을 고정하므로 이미 닫힌 DSL이다. 분기·루프·산술식을 넣지 않는다.
  • L3 함수 — 프로젝트별 코드(workers). 에이전트가 생성하고 sandbox에서 실행한다. 커밋하지 않는다 — 서버가 준 읽기 컨텍스트와 파라미터를 받아 GraphEdits를 반환하며, DB에 접근하지 않는다. 현행 워커 SDK는 호출마다 커밋하므로 편집 서술 반환으로 전환한다(전환 전까지 워커의 다중 쓰기는 원자적이지 않음을 알려진 한계로 둔다).

단일 커밋 경로. 편집이 L2 폼에서 왔든 L3 코드에서 왔든, 서버가 닫힌 op 집합·property_schema·권한·criteria를 검증한 뒤 한 트랜잭션에서 커밋한다(aggregate root 행 락 + 감사 기록). L2와 L3의 차이는 “그 편집을 누가 계산했나”뿐이다.

Aggregate 경계는 노드 설계의 1차 결정이다. 독립적으로 참조되고 수명이 다른 것만 노드로 만든다. 종속 세부는 properties 또는 엣지 properties로 둔다. 예: 분개행은 노드가 아니라 전표 → 계정 엣지의 properties다.

무결성은 3층으로 구성한다.

  • Action 경로(앱) — 타입·필수·열거값·업무 규칙. 사용자와 에이전트가 읽는 에러 메시지가 여기서 나온다. [ACTION-01] 단일 경로가 정책 + harness 스캔으로 강제되므로 이것이 1차이자 실질 방어선이다.
  • Aggregate 행 락(앱, 트랜잭션 내) — SELECT … FOR UPDATE로 check-then-write 레이스를 제거한다. 편집·검증·감사가 한 트랜잭션에 있다.
  • Reconciliation 잡 — 전 노드를 property_schema로 재검증하고 집계를 재계산해 대조한다. DB 제약이 없으므로 사후 감사가 곧 정합성 증명 수단이다.

불변식은 L3이다 — DB 트리거를 두지 않는다. 초안은 node_catalog.invariants + 범용 deferred constraint trigger로 “Action 우회 쓰기”를 막으려 했다. 두 가지 이유로 철회한다. (1) 우회 경로(admin·seed·psql·다른 클라이언트)는 [ACTION-01]이 정책으로 닫고 harness가 검사하므로, 트리거가 지킬 대상이 없다. (2) 사용자가 액션을 직접 만들면 필요한 불변식도 직접 만든다 — 재고·인사·법무마다 새 kind가 필요해지고, “ADR을 쓰고 kind를 추가한다”는 규율은 사용자가 기다리지 않는 순간 무너진다. 그 결과가 plpgsql 안에서 kind 분기가 늘어나는 것이고, 이는 삭제된 executeAction이 SQL로 부활하는 경로다. 따라서 여러 행에 걸친 업무 불변식(차대 균형·시산표·재고 하한 등)은 L3 함수가 트랜잭션 안에서 락 이후 상태를 읽고 검증한 뒤 GraphEdits를 반환하는 방식으로 표현한다. 표현력은 코드라 무제한이고 새 도메인이 새 kind를 요구하지 않는다. Palantir도 같다 — 온톨로지 불변식은 Function(코드)이지 DB 제약이 아니다.

Invariant 개정

  • [ARCH-03] 폐기 — “legacy generic runtime 복원 금지”를 삭제한다. 금지 대상이 “범용 액션”이 아니라 “행동을 데이터로 두는 인터프리터”였음을 아래 규칙으로 정밀화한다.
  • [ACTION-01] 신설 — 모든 그래프 쓰기는 Action 커밋 경로를 지난다. seed·admin script·MCP·에이전트에 예외를 두지 않는다.
  • [ACTION-02] 신설 — GraphEdits op는 닫힌 집합이다. criteria는 Gate Policy 문법(parseGatePath)을 재사용하며 새 kind 열거를 만들지 않는다. 어느 쪽이든 확장은 ADR을 요구한다. 검증 어휘(criteria kind·DB 불변식 kind)를 새로 만들지 않는다 — 어휘로 표현되지 않는 검증은 L3 코드다.
  • [ACTION-03] 신설 — L3 함수는 커밋하지 않고 편집을 서술한다. sandbox 코드에 DB 접근을 주지 않는다. 현행 워커 SDK의 직접 커밋(graph.createNode 등)은 이 규칙 위반으로 등록하고 전환 대상으로 추적한다.
  • [ACTION-04] 신설 — 생성된 L3 함수는 함께 생성된 테스트 통과를 실행 전제로 한다.
  • [GRAPH-02] 강화 — “GraphWritePort로만”을 “Action 커밋 경로로만”으로 좁힌다.
  • [GRAPH-05] 구현 + 확장 — 현재 이 룰은 문서만 있고 미구현이다(edge domain/range 미검증, validateEdgeProperties no-op, 런타임 정의 타입의 property_schema 미사용). 먼저 구현한다(P0에서 완료). DB 불변식 컬럼은 두지 않으므로 검증 대상 확장은 없다.
  • [GRAPH-03] [GRAPH-04] [GRAPH-06] 유지 — org/teamspace 격리, 인스턴스 → catalog FK only, 노드 봉투 = title + properties. 이 결정이 오히려 강화한다.
  • [GRAPH-08] 무관 — 트랜잭션 화면 typed React 원칙은 그대로 두며 ADR-persona-workspaces-with-explicit-workflow-pages도 유효하다.

Consequences

  • 타입과 액션이 릴리즈 없이 늘어난다. 사용자·에이전트가 도메인을 저작할 수 있다.
  • 커밋 경로가 하나라 권한·감사·트랜잭션이 한 곳에 모인다. MCP 도구 표면과 UI 폼이 같은 선언에서 생성된다.
  • 대가: DB가 properties의 타입도, 행 간 불변식도 검사하지 않는다. Action 단일 경로와 reconciliation 잡은 편의 기능이 아니라 하중을 받는 구조물이다. [ACTION-01]이 뚫리는 순간 방어선이 0이므로, 우회 경로는 harness 스캔이 상시 검사하고 예외는 allowlist에 사유와 함께만 둔다.
  • 현재 이 방어선은 비어 있다. 위 실측대로 런타임 정의 타입은 properties가 무검증 통과하고, 엣지는 domain/range·properties 모두 검증되지 않는다. 즉 “앱이 유일 방어선”이라는 전제가 아직 성립하지 않으므로 검증 층 구현이 이 결정의 첫 작업이며, 그 전에 런타임 타입 저작을 사용자에게 개방하면 오염을 막을 수단이 전혀 없다.
  • 대가: cross-domain 참조에 FK를 쓸 수 없다. 참조 무결성은 엣지 + criteria로 표현하며 on delete 같은 DB 시맨틱을 잃는다.
  • 대가: 집계는 뷰·expression index·stored generated column 승격에 의존한다. 계정 잔액 같은 파생값은 액션이 갱신하지 않고 읽기 전용 뷰로 둔다.
  • 대가: L3은 sandbox 부팅 레이턴시가 있다. L2로 표현되는 것은 L2로 둔다.
  • 위험: L2 어휘에 표현력을 더하려는 압력이 지속된다. 이 압력에 굴복하는 것이 과거 실패 경로다.
  • 위험: 생성된 L3 함수의 정확성을 인간 리뷰가 보증하지 않는다. [ACTION-04]가 그 자리를 대체하며, 없으면 이 구조는 규칙 DSL보다 위험하다.
  • 프로젝트별 함수의 버전 관리 방식(카탈로그가 sandbox_sources 버전을 참조)은 후속 결정으로 남긴다.

Alternatives considered

  • 도메인별 관계형 테이블(선행 결정) — DB 제약·FK·트랜잭션이 가장 강하지만 타입 추가가 마이그레이션에 묶여 런타임 도메인 정의가 불가능하다. 출하 타입만 있는 제품이라면 이쪽이 옳다.
  • 데이터 레이크(Palantir 그대로) — 타입별 스키마를 마이그레이션 없이 얻지만, OLTP 서빙을 위한 별도 인덱싱 층·파이프라인 운영이 현 단계 규모에 과하다. 분석이 서빙을 압박하는 시점에 CDC로 파생 레이크를 뽑는 쪽이 순서상 맞다.
  • 런타임 DDL — 타입마다 실제 CREATE TABLE. 테넌트 × 타입만큼 테이블이 늘어 Postgres 카탈로그가 감당하지 못한다.
  • 규칙 DSL로 로직까지(과거 executeAction) — 표현력 상한과 타입 안전성 상실로 이미 실패했다. L2를 닫힌 집합으로 유지하고 그 이상을 L3 코드로 넘기는 것이 이 결정의 핵심 차이다.
  • 타입별 테이블 + 범용 테이블 하이브리드 — 출하 도메인은 테이블, 사용자 정의는 노드. 무결성은 최선이지만 저장 전략이 둘이라 포트·쿼리·마이그레이션이 이중화된다. 런타임 정의를 1급 목표로 두는 이상 단일 전략을 택한다.
