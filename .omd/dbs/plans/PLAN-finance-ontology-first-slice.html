Goal

3층 구조의 비어 있는 부분만 채워 회계 액션 3개로 수직 관통한다. 저장소 감사 결과 L1 저장·저작과 L3 실행은 이미 있고, 실제 갭은 (a) 카탈로그 검증 층, (b) Gate 위의 쓰기 봉투, (c) 워커 커밋 모델 세 가지다. 이 슬라이스의 산출물은 회계 기능이 아니라 그 세 갭이 닫혔다는 증거와 L2/L3 경계 판정이다.

실측 기준선

ADR의 “현행 구현 실측” 절이 근거다. 이 PLAN은 이미 있는 것을 다시 만들지 않는다.

  • 이미 있다 — 만들지 않는다: node_catalog/edge_catalog의 스키마 컬럼, CatalogWritePort, agent-runtime create_node_type/create_edge_type, Gate Policy 엔진(when·match·require[]·onFail·onPass.effects + parseGatePath), workers 테이블과 executeWorker(inputSchema 검증·dryRun·permissions·SDK 브리지·runEphemeralSandbox), agent_runs 로그.
  • 비어 있다 — 이 슬라이스가 채운다: 런타임 정의 타입의 properties 검증, 엣지 domain/range 검증, validateEdgeProperties, 액션 파라미터 스키마·편집 op 어휘·권한·감사·단일 트랜잭션, 워커 SDK의 편집 서술 전환.

Approach

검증 층을 먼저 닫는다. 현재 런타임 정의 타입은 무검증 통과하므로 “앱이 유일 방어선”이라는 ADR 전제가 성립하지 않는다. 액션 봉투를 먼저 만들면 방어선 없는 경로 위에 봉투를 씌우는 셈이다.

그 다음 Gate를 criteria로 재사용해 액션 봉투를 얹는다. criteria 어휘를 새로 만들지 않는다 — require[]의 경로 표현식이 이미 그래프 순회 + count{min,max}를 지원한다. 회계에 필요한 것이 이 문법으로 표현되는지가 시험대이며, 표현되지 않으면 문법을 늘리지 말고 L3 필요로 기록한다.

액션 3개는 난이도 순이 아니라 L2 경계를 가로지르는 순으로 고른다.

  • finance.post_journal_entry — L2로 되어야 한다. 차대 균형은 Gate require의 count/경로로 표현되거나, 안 되면 node_catalog.invariants의 sum_balance로 간다.
  • finance.close_fiscal_period — L2 경계 시험. 시산표 검증이 Gate 문법으로 표현되는가. 여기서 문법을 늘리고 싶은 압력이 처음 발생하며, 굴복하는지가 이 슬라이스의 진짜 시험이다.
  • finance.void_journal_entry — L3 예상. 기존 엣지를 읽어 차·대를 뒤집으므로 편집이 파라미터에서 파생되지 않는다. 워커 커밋 모델 전환의 첫 실사용례가 된다.

Aggregate 경계는 전표를 root로 둔다. 분개행은 노드가 아니라 전표 → 계정 엣지이고 금액은 엣지 properties에 산다. 원장은 append-only이며 취소는 역분개로 처리한다.

거부 케이스를 먼저 작성한다([TEST-01]). 통과 케이스만으로는 이 설계가 진짜인지 판명되지 않는다.

Steps

P0 — 검증 층 (갭 a) — ✅ 완료 (2026-08-18)

판정. property_schema 저장 형식은 닫힌 JSON Schema 서브셋 → Zod 컴파일로 확정했다(ajv 미도입, contracts는 zod 단일 의존 유지). 런타임 정의 타입은 이제 property_schema가 유일 방어선으로 실제 강제되고, edge domain/range도 create-edge에서 강제된다([GRAPH-05] 문서-구현 불일치 해소). 남긴 판단: 출하 타입의 하드코딩 Zod(superRefine·union 포함)는 서브셋으로 손실 없이 내릴 수 없어 시드는 여전히 빈 스키마를 쓰고 Zod가 보강 검증한다 — 출하 타입을 카탈로그 스키마로 단일화할지는 별도 결정.

  1. property_schema를 실제 validator로 쓴다. validateNodeProperties가 isKnownNodeType이 아닐 때 무검증 통과하는 경로를 없애고, 카탈로그 행의 property_schema로 검증한다. 스키마 표현은 기존 하드코딩 Zod와 상호 변환 가능한 형태로 고정한다.
  2. validateEdgeProperties를 구현한다(현재 전 타입 no-op).
  3. create-edge에서 domain_catalog_ids/range_catalog_ids를 강제한다. [GRAPH-05]의 미구현 항목이며 문서-구현 불일치를 닫는다.
  4. 거부 케이스: 스키마 위반 properties · domain 위반 엣지 · range 위반 엣지 · 런타임 정의 타입의 잘못된 properties.

P1 — 액션 봉투 (갭 b)

  1. GraphEdits 닫힌 op 집합(create_node·update_properties·create_edge·delete_edge·set_status)을 packages/contracts에 Zod로 정의한다. criteria는 정의하지 않고 Gate를 참조한다.
  2. 액션 선언 계약 — key·parameters(Zod)·writes·requires(권한)·criteria(Gate 정책 키 참조)·gate(승인 필요 여부).
  3. runAction 커밋 경로 — 파라미터 파싱 → Gate 평가(evaluateGatePolicies 재사용) → 권한 확인 → aggregate root SELECT … FOR UPDATE → 편집 적용 → 감사 기록. 한 트랜잭션.
  4. finance.* 카탈로그 시드 — finance.account·finance.fiscal_period·finance.journal_entry 노드 타입과 posts_to·in_period·reverses 엣지 타입. property_schema와 domain/range 포함.
  5. 액션 1 — post_journal_entry를 L2만으로 구현.
  6. 액션 2 — close_fiscal_period. Gate 문법으로 표현되는지 판정하고, 안 되면 문법을 늘리지 말고 L3 필요로 기록.

P2 — DB 불변식 + 워커 커밋 모델 (갭 c)

  1. node_catalog.invariants 컬럼 + nodes의 범용 deferred constraint trigger. WHEN 절이 아니라 함수 본문에서 카탈로그를 조회해 org별 uuid 하드코딩을 피한다. 평가기는 sum_balance만 지원한다.
  2. 워커 SDK를 편집 서술 반환으로 전환한다 — graph.write.* 직접 커밋을 GraphEdits 반환으로 바꾸고 runAction이 커밋한다. [ACTION-03] 위반 해소.
  3. 액션 3 — void_journal_entry. 전환된 워커 경로의 첫 사용례.
  4. 거부 케이스 추가: 불균형 전표가 COMMIT 시점에 거부 · 동시 쓰기 2건 중 하나 거부 · 마감 기간 쓰기 거부 · Action 우회 직접 INSERT가 trigger에 걸림.
  5. 파생 조회 — account_balances 뷰. 액션이 잔액을 갱신하지 않음을 확인.
  6. reconciliation 스켈레톤 — 전 노드 property_schema 재검증 + 집계 대조 리포트.
  7. 판정 기록 — L2/L3 경계 결과를 ADR에 반영한다. 항목별 판정 없이 슬라이스를 닫지 않는다.

비범위: sandbox 부팅 최적화, 프로젝트별 함수 버전 관리(카탈로그가 sandbox_sources 버전을 참조하는 설계), [ACTION-04]의 생성 테스트 게이트, 회계 도메인 완성. P0가 닫히기 전에는 런타임 타입 저작을 사용자에게 개방하지 않는다.

Risks

  • P0를 건너뛰려는 유혹 — 액션 봉투가 더 눈에 보이는 진전이라 먼저 하고 싶어진다. 그러면 방어선 없는 경로 위에 봉투를 씌우는 것이고, ADR이 하중 구조물이라 부른 것이 비어 있는 상태로 남는다.
  • Gate 문법 확장 압력 — 가장 큰 위험이며 과거 executeAction이 죽은 경로다. 10단계에서 require 문법을 늘리고 싶어지면 그 자체를 신호로 취급하고 L3으로 넘긴다. plpgsql 평가기가 30줄을 넘으면 경고([ACTION-02]).
  • property_schema 표현 형식 결정 — 기존 하드코딩 Zod와 DB jsonb 스키마의 상호 변환이 P0의 실질 난점이다. 여기서 형식을 잘못 고르면 출하 타입과 런타임 타입이 두 갈래로 갈린다.
  • 워커 SDK 전환의 파급 — 기존 워커 스크립트가 graph.write.*를 직접 호출하고 있으면 호환이 깨진다. 전환 범위와 마이그레이션 경로를 12단계에서 먼저 조사한다.
  • Aggregate 경계 오판 — 분개행을 노드로 만들면 균형 검증이 aggregate를 벗어나 락 범위가 무너진다. 8단계 시드에서 이 경계를 고정한다.
  • 집계 성능 — 엣지 properties의 JSONB 합산. 필요 시 edges에 stored generated column 승격 + 부분 인덱스. 측정 후 대응한다.
  • 슬라이스 비대 — 회계 도메인을 완성하려는 유혹. 산출물은 갭 3개가 닫혔다는 증거와 경계 판정이다.

Verification

  • pnpm test --filter @ssota/contracts — 닫힌 op 스키마, property_schema 표현 형식.
  • pnpm test --filter @ssota/core — 순수 회계 함수(차대 균형·기간 판정·역분개 생성)와 Gate 평가. DB 없이 통과해야 한다.
  • pnpm test --filter @ssota/adapter-postgres — 거부 케이스 8종(P0의 4종 + P2의 4종). 통과 케이스보다 먼저 그린이 되어야 한다.
  • 마이그레이션 up/down 확인 — Tier 3.
  • [GRAPH-05] 문서-구현 일치 확인 — edge domain/range 검증이 실제로 동작하는 테스트가 있는지.
  • L2/L3 경계 판정이 ADR에 반영되었는지 확인. 이 항목 없이 슬라이스를 닫지 않는다.
