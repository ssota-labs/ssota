# Seed × Agent Kit plan (도메인 툴 생성 시스템)

> 상태: draft · 2026-07-03 · 선행 문서: [runtime-workspace-sandbox-plan.md](runtime-workspace-sandbox-plan.md)
> 이 문서는 self-contained다 — 배경 리서치 원본(mirror-dimension 비공개 레포)에 접근하지
> 못해도 아래 Background 섹션만으로 읽을 수 있다.

## Summary

ssota 에이전트가 **씨앗(Seed)** 을 받아 Sandbox Environment 안에서 독립된 도메인 툴
(WebGL 디자인 툴, 투자 지표랩, PPT 템플릿, 회로 시뮬레이터, 교육 자료 등)을 만들어
배포하고, 그 툴이 만든 결과물을 아티팩트로 환류시키는 시스템의 설계안이다.

Toolcraft가 증명한 방법론(스타터 + 에이전트 하네스 + 기계 검증)을 ssota 구조에 맞게
재배치한다. 핵심 재배치는 세 가지다:

1. **정본 분리** — 코드 몸체(Seed)는 blob, 지침+검증기(Agent Kit)는 에이전트 정의,
   그래프에는 **결과물만** 올린다. 툴·씨앗을 그래프 노드로 만들지 않는다 (v1).
2. **지침과 검증기의 동거** — Toolcraft는 "테스트가 문서를 검사"하는 장치로 지침-검증기
   드리프트를 막았다. 우리는 둘을 **같은 Agent Kit 폴더에 한 버전으로** 묶어 원천 차단한다.
3. **판정 외부화** — 에이전트의 "통과했다"는 자기 보고를 믿지 않는다. 완료 판정은
   제품 서비스(오케스트레이터)가 Sandbox 밖에서 수집한 실행 결과로만 확정한다.

sandbox plan의 open-agents 원칙(에이전트는 VM 밖, `sandbox_*` 프리미티브로 제어,
자격증명은 제품 서비스가 브로커)을 그대로 전제한다.

## Background — 이 방법론은 어디서 왔나

**Toolcraft**(@pixel-point/toolcraft)는 외부 상용 스타터킷으로, 코딩 에이전트가
디자이너용 그래픽 툴을 만들 때 스타터 코드 + 에이전트 지침 + 기계 검증을 한 패키지로
제공한다. 핵심 문제의식은 두 가지고, 이 플랜의 무거운 검증 장치들은 전부 여기서 나왔다:

1. **AI가 만든 툴은 "그럴듯하게 생겼는데 실제로 안 움직인다"** — 해법: "화면에 보이는
   모든 상호작용은 실제 조작 후 산출물의 관찰 가능한 변화로 증명한다"는 기계 검증.
2. **에이전트는 "했다고 친다"** — 검증 없이 완료를 보고하는 실패 모드를 선언↔테스트
   기계 대조와 작업 기록 대조로 차단.

이 플랜의 메타 검증 엔진·Journal·실행 영수증·판정 외부화는 전부 이 방법론의 재배치다.
**라이선스 경계**: Toolcraft는 독점 라이선스라 코드·문서 텍스트를 가져다 쓸 수 없다 —
채택하는 것은 방법론(개념)뿐이고 모든 코드·문구는 자체 작성한다.

**mirror-dimension**은 같은 방법론으로 진행 중인 별도 트랙(디자이너용 퍼블릭 SaaS,
비공개 레포)이다. 본 문서는 그쪽 스펙을 읽지 않아도 완결되도록 작성됐다.

### 용어

| 용어 | 정의 |
|---|---|
| **수용 매트릭스** | 툴이 스스로 선언하는 검증 항목 목록. 항목 = 사용자 행동 + 기대되는 관찰 가능한 변화 + 뒷받침 테스트 이름. "보이는 모든 것은 동작을 증명한다"의 선언부 |
| **판정기(Judge)** | 조작 전후 산출물의 지문(픽셀 해시 등)을 채취·비교해 "실제로 변했는가"를 판정하는 도구 |
| **Journal** | 에이전트가 작업 중 결정·근거·검증 결과를 남기는 작업 로그. 완료 게이트의 입력 |
| **실행 영수증** | 체크 러너가 매 실행 남기는 기계 판독 기록. Journal의 "통과했다" 주장을 대조하는 근거 — 영수증 없는 통과 주장은 거부된다 |

## Goals

- 씨앗 1종(WebGL 디자인 툴)으로 end-to-end 성장 파이프라인 검증 (v1).
- Seed·Agent Kit·실행 기록의 버전이 태스크 레코드에 증거로 남는 구조.
- 에이전트가 검증을 우회·변조할 수 없는 완료 게이트.
- 툴 결과물(내보내기 파일)이 ssota 아티팩트로 저장되는 환류 경로.
- **추상화 경계 확립 — 1호의 성공 기준은 "디자인 툴이 나왔다"가 아니라
  "A층(섀시)에 도메인 코드(픽셀)가 한 방울도 안 묻었다"이다** (§추상화 3층 참조).
  이 경계가 2호 씨앗의 비용을 결정한다.

## Non-goals (v1)

- 씨앗 마켓·서드파티 씨앗 생태계. 씨앗은 내부 제작만.
- 툴·씨앗의 그래프 노드화. 결과물(아티팩트)만 저장한다.
- npm 패키지 배포 체계. v1은 blob tarball로 충분하다 — 이미 자란 툴에 대한
  업데이트 전파가 필요해지는 시점에 npm 전환을 검토한다.
- 멀티테넌트 퍼블릭 서비스 (그건 mirror-dimension 트랙).

## 추상화 3층 — 무엇이 섀시이고 무엇이 씨앗인가

Toolcraft 하네스의 메커니즘은 깔끔한 이분법이 아니라 3층으로 갈린다.
**"에이전트를 규율하는 절차"는 전부 추상화되고, "동작함의 정의"는 전부 도메인에 남는다.**

### A층 — 순수 섀시 (도메인 불변, 한 번만 구현 → Agent Kit + CLI)

| 메커니즘 | 도메인 불변인 이유 |
|---|---|
| 단계형 워크플로우 엔진 (단계 전이·회귀 판정) | 통과조건의 "내용"은 게이트 결과에 위임 — 절차만 소유 |
| Journal + 실행 영수증 대조 (완료 게이트) | 주장 vs 실행 기록 대조일 뿐, 내용을 안 봄 |
| 판정 외부화 (fresh kit 재주입, exit code/리포트 수집) | 오케스트레이션 계층 |
| CLI 골격 (종료 코드 규약, `--json` 스키마, 비대화형, 커맨드 세트) | 에이전트-CLI 인터페이스는 씨앗 무관 |
| 무결성 모델 (해시 매니페스트 or 버전 핀 + 영역 경계) | 파일 보호는 내용을 안 봄 |
| dev 서버 신원 핸드셰이크 + 포트 조정 | 순수 배관 |
| 스캐폴딩 파이프라인 (복사 + 이름 주입 + 신원 발급) | 템플릿 내용과 무관한 실행기 |
| **수용 매트릭스 메타 검증 엔진** (선언 항목↔실재 테스트 대조, 주석 제거 정적 분석) | "선언과 테스트의 정합"만 검사 — Toolcraft 최대 발명이자 도메인 무관 |
| 룰 카탈로그 **프레임** (룰 ID·룰 레벨 위계·카탈로그↔검증기 동기화 자기 검증·실패 메시지=에이전트 지시문) | 룰을 담는 그릇과 드리프트 방지 장치 |

### B층 — 프레임은 섀시, 구현은 씨앗 (플러그 인터페이스 — 승부처)

| 메커니즘 | 섀시가 소유하는 프레임 | 씨앗이 꽂는 구현 |
|---|---|---|
| **판정기(Judge)** | 지문 채취→전/후 비교→변화 대기 타임아웃 | 채취기: 픽셀 해시(디자인)/수치 diff(투자)/슬라이드 DOM(PPT)/시뮬 출력(회로) |
| 성능 예산 | 선언 단일화·조회 API·완화 규율 | **지표 자체**: 프레임 간격(실시간 렌더) vs 백테스트 소요시간 vs 내보내기 시간 |
| 부하 프리셋 | "테스트는 프리셋을 조회해서만" 강제 | 무엇이 스트레스인가: 4096px 이미지 vs 10년 틱 데이터 vs 100노드 회로 |
| 증거 유형 | 유효/무효 증거 레지스트리 구조 | 도메인별 유효 증거 목록 |
| 치팅 차단 | 구조 패턴 (상태 직접 주입 금지, 판정기 우회 금지) | 도메인 패턴 (해상도 몰래 낮춰 통과 금지 등) |
| 컨트롤 조립 | 선언→패널 자동 조립 + 커스텀 렌더러 탈출구 | 도메인 컨트롤 (지표 파라미터 에디터, 부품 팔레트) |
| 익스포트 | 진행/취소/파일명/산출물 이벤트 | PNG·비디오 vs CSV·리포트 vs pptx vs 넷리스트 |

### C층 — 순수 도메인 (씨앗마다 새로, 추상화 시도 자체가 낭비)

- 스캐폴드 템플릿 내용, Surface 렌더 계약, 도메인 지침 부록(`instruction.domain.md` — 도메인 규칙·렌더 기법 가이드), 레퍼런스 툴
- 판정기의 **채취기 구현**과 **스트레스의 정의**는 인터페이스를 아무리 잘 그어도 도메인
  지식 그 자체 — 씨앗마다 진짜 엔지니어링 비용이 든다 (씨앗 계획 시 이걸 만만하게 보지 말 것)
- ⚠️ **PPT의 멀티 페이지/컬렉션 구조는 B층 플러그로도 안 된다** — "단일 상태 트리 +
  단일 Surface"라는 프레임 가정 자체를 깨므로 런타임 구조 확장이 선행돼야 하는 별개 급 작업
  (2호로 투자 지표랩을 미는 이유)

### 1호 구현 규율 (과추상화 방지)

1. **A층은 처음부터 분리** — 픽셀 해시 로직이 워크플로우 엔진·메타 검증기 안으로 새면 실패.
2. **B층은 "파일 경계만"** — v1에서 정식 플러그인 API를 만들지 않는다. `judge/`,
   `budgets/`, `presets/` 처럼 도메인 코드를 별도 모듈로 격리만 해두고, 2호(투자)에서
   그 파일들을 교체해보며 인터페이스를 발견한다 (rule of three 전에 API 확정 금지).
3. **C층은 고민 없이 씨앗에.**

## Product concepts

### Seed

한 도메인의 툴을 낳는 코드 페이로드. **blob 버킷에 버전 있는 tarball**로 저장한다.

```
seed-webgl@1.0.0.tar.gz
├─ template/          # [C층] 스캐폴딩되는 프로젝트 뼈대 (설정 선언, 소스 진입점)
├─ runtime/           # [B+C층] 툴 런타임·컨트롤 (v1: 벤더링 방식 — 단순 우선)
│                     #   범용 컨트롤 조립은 B, Surface 렌더 계약은 C
├─ checks/            # [B층 구현] 도메인 검증 플러그 — 판정기 채취기(픽셀 해시),
│   ├─ judge/         #   예산 지표, 부하 프리셋, 도메인 치팅 패턴.
│   ├─ budgets/       #   v1 규율: 정식 플러그인 API 없이 이 파일 경계로만 격리
│   └─ presets/       #   (2호에서 교체해보며 인터페이스 발견)
└─ instruction.domain.md  # [C층] 도메인 지침 부록 — 주입 시 kit의 instruction.md(공통)와
                          #   함께 에이전트에 제공된다
```

- v1은 Toolcraft식 벤더링(전부 프로젝트로 복사)을 채택한다 — 이후 의존성이 없어
  tarball 하나로 완결되고, fetch+extract가 곧 설치다.
- 씨앗 발행 게이트: **"이 씨앗으로 레퍼런스 툴을 실제로 길러 최종 검증을 통과"** 가
  씨앗 버전의 CI다. 미검증 씨앗은 발행되지 않는다.
- ⚠️ 클린룸: 씨앗의 코드·문서는 전부 자체 작성한다. Toolcraft 코드·문구는 방법론
  참고까지만 (Background의 라이선스 경계 참조).

### Agent Kit

에이전트 정의가 참조하는 **폴더 하나** — "프롬프트 + 자기 검증 도구를 든 에이전트".

```
agent-kits/tool-builder/     # 정본: git (에이전트도 리뷰·CI 대상) — 전체가 [A층]
├─ instruction.md            # 에이전트 지침 (워크플로우, 판단 규칙, 금지 사항)
├─ rules.ts                  # 룰 카탈로그 프레임 — 타입 있는 데이터, 지침과 같은 버전으로 이동
└─ checks/                   # 씨앗 무관 검증 실행기: 워크플로우·구조 검사, 메타 검증 엔진,
                             #   완주 게이트, Journal↔영수증 대조.
                             #   B층 "프레임"(판정기 인터페이스·예산 조회·프리셋 강제)도 여기 —
                             #   구현은 seed의 checks/에서 로드한다
```

**A층 오염 감시**: kit/CLI 코드에 도메인 지식(픽셀, 프레임 간격, 특정 컨트롤명)이
들어오면 리뷰에서 반려한다. 이것이 Goals의 1호 성공 기준이다.

- 지침(에이전트가 읽는 것)과 검증기(에이전트를 잡는 것)가 **같은 폴더, 같은 버전**.
- 정본은 git, Sandbox 주입용 스냅샷만 blob에 발행한다.
- ssota 에이전트 정의(instruction)는 kit 버전을 참조한다: `tool-builder@v3`.

### Grow 태스크

씨앗 → 툴 성장의 실행 단위. 기존 태스크/워크플로우 컨벤션에 `work.grow_seed`로 등록.

### 부팅 스택 (변경 주기 순 4층)

```
Sandbox Environment (runtime profile: 예 sandbox.seed_webgl)
├─ base 스냅샷            : node·pnpm·headless 브라우저 (거의 불변 — 부팅 고속화)
├─ Agent Kit 주입          : /opt/agent-kit (워크스페이스 밖! — 산출물·스냅샷에 안 섞임)
├─ Seed fetch/extract      : 워크스페이스에 전개
└─ workspace              : 에이전트가 작업하는 툴 인스턴스
```

Kit은 **오케스트레이터가 push 주입**한다 (에이전트 셀프 다운로드 금지 — 버전 증명이
에이전트 자기 보고가 되고, 세팅 누락·네트워크 의존이 생긴다).

## 실행 플로우

```
1. 태스크 생성 (씨앗@버전, kit@버전 명시)
2. Sandbox Environment 부팅 (base 스냅샷)
3. 오케스트레이터: kit 주입 (/opt/agent-kit) + seed 전개 (workspace)
4. 에이전트 런 — VM 밖에서 sandbox_* 프리미티브로 조립 작업.
   작업 중 kit/seed의 체크를 자유롭게 실행 (빠른 피드백 — 이것이 kit을 들려 보내는 이유)
5. 최종 판정 — 오케스트레이터가:
   a. kit을 fresh 재주입 (에이전트의 체크 변조 무효화)
   b. 체크 러너를 직접 기동 (에이전트 도구 호출 아님)
   c. exit code + 기계 판독 리포트를 Sandbox 밖에서 수집
6. 통과 시: 정적 빌드 → 배포 → URL·버전 기록
7. 결과물 환류: 툴에서 내보낸 파일 → ssota 아티팩트로 저장
8. 워크스페이스 스냅샷 저장 (sandbox plan의 persist/resume 그대로)
```

### 판정 외부화 — 세 규칙

1. 태스크 기록의 kit/seed/base 버전은 오케스트레이터가 쓴다 (에이전트 보고 아님).
2. 에이전트의 "통과" 텍스트만으로 완료 상태 전이가 일어나지 않는다.
3. 최종 체크는 fresh kit 재주입 후 오케스트레이터가 기동한다 — 에이전트가 워크스페이스
   안팎의 체크 코드를 어떻게 고쳤든 판정에 영향을 못 준다.

## 결과물 환류

- 배포된 툴은 정적 SPA. 내부 페이지에서 iframe 임베드 가능.
- 툴 안에서 내보내기 발생 시 다운로드 대신 postMessage로 호스트에 전달 →
  아티팩트 저장 (embedded 모드 — 툴 런타임에 호스트 브릿지 이벤트 훅 필요).
- v1은 저장·목록·다운로드까지만. 아티팩트 간 파생 관계 추적은 후속.

## 단계 계획

- **P1** Seed tarball 규약 + blob 버킷 + fetch/extract (sandbox setup script로).
  tarball 내부에서 B층 구현(`checks/judge·budgets·presets`)의 파일 경계를 처음부터 강제
- **P2** Agent Kit 구조 + push 주입 + `tool-builder` kit v1 작성 — **A층 전체가 여기서 완성**
  (씨앗을 몰라야 정상: kit 코드에 도메인 단어가 나오면 설계 오류)
- **P3** `work.grow_seed` 태스크 플로우 + 판정 외부화 (fresh 재주입 + 외부 수집)
- **P4** 정적 배포 + 아티팩트 환류 (embedded 모드 postMessage 브릿지)
- **P5 (2호 씨앗 시점)** 투자 지표랩 씨앗을 만들며 B층 파일들을 교체 → 실제로 갈린 지점을
  플러그 인터페이스로 승격 (rule of three — 이때가 API 확정 시점)
